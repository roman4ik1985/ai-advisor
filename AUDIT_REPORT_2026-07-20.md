## 1. Итог

Прототип пригоден для локального тестирования в CLI-режиме. Базовая архитектура компактна, секреты не обнаружены, frontend безопасно выводит ответы через `textContent`, CLI ограничен loopback/read-only, а текущие семь unit-тестов проходят.

До production требуется закрыть три приоритетных направления:

1. отделить доверенные инструкции модели от пользовательского и HTML-контекста;
2. привести публичный API к стабильному контракту ошибок и production-защите от нагрузки;
3. исправить семантику модального окна, возврат фокуса и контраст вторичного текста.

Критических находок уровня P0 нет. Найдено 4 требования уровня P1, 11 уровня P2 и 5 улучшений уровня P3.

## 3. Архитектурный аудит

### Сильные стороны

- backend, prompt, каталог и AI-провайдеры разделены по модулям;
- CLI/API переключаются конфигурацией без изменения frontend;
- CLI принудительно слушает только `127.0.0.1`;
- состояние диалога не сохраняется долгосрочно;
- внешний каталог и AI имеют тайм-ауты;
- сбой виджета изолирован от основных функций магазина.

### Находки

#### ARCH-01 — P1: нет ограничения параллельных AI-запросов

В `server.mjs` каждый разрешённый POST сразу запускает CLI-процесс или API-запрос. При всплеске трафика это может исчерпать CPU, процессы, соединения или API-бюджет.

Рекомендация: semaphore/очередь с ограничением параллелизма, максимальной длиной очереди и ответом 503/429 при backpressure.

#### ARCH-02 — P1: rate limit не готов к production

`server.mjs:16,92-100` использует `Map` в памяти. Ключи не очищаются, состояние не разделяется между процессами, а `remoteAddress` за reverse proxy может быть одинаковым для всех посетителей.

Рекомендация: Redis или иной общий limiter; доверенный proxy-chain; TTL; отдельные лимиты на IP/сессию и глобальный бюджет.

#### ARCH-03 — P2: парсер каталога привязан к одному HTML-шаблону

`src/catalog.mjs:1` зависит от класса `.product-name` и регулярного выражения. Изменение шаблона OpenCart может незаметно вернуть пустой каталог.

Рекомендация: выделить OpenCart adapter, добавить fallback-селекторы, нормализацию канонического URL, контрактный fixture реального HTML и метрику пустых результатов.

#### ARCH-04 — P2: отсутствует управляемое завершение процесса

Нет обработчиков SIGINT/SIGTERM, прекращения приёма запросов и ожидания активных операций.

Рекомендация: graceful shutdown с ограниченным drain timeout.

#### ARCH-05 — P3: `/health` проверяет только процесс

Endpoint не различает liveness и readiness и не проверяет готовность конфигурации/зависимостей.

Рекомендация: оставить `/health` как liveness и добавить `/ready` без вызова платного AI на каждый probe.

## 4. Security quick scan

### Пройдено

- `OPENAI_API_KEY` в локальном `.env` пуст;
- `.env` включён в `.gitignore`;
- внешних npm-зависимостей нет;
- API-ключ передаётся только сервером;
- Responses API вызывается с `store: false`;
- пользовательские ответы вставляются через `textContent`, не через `innerHTML`;
- request body ограничен 64 КБ;
- присутствуют `nosniff`, Referrer-Policy и Permissions-Policy;
- CLI использует ephemeral/read-only режим и временную директорию.

### Находки

#### SEC-01 — P1: доверенные и недоверенные данные объединены в один prompt

`src/prompt.mjs` формирует строку с правилами, сообщениями и HTML-контекстом, а `src/providers/api-provider.mjs:14` отправляет её как единый `input`. Пользователь или содержимое страницы могут попытаться переопределить правила.

Рекомендация: в Responses API передавать правила через отдельное поле доверенных инструкций, а данные — структурированным input; для CLI использовать жёсткие delimiters и тесты на prompt injection. Любые товарные действия строить по структурированному `catalog`, а не по свободному тексту модели.

#### SEC-02 — P2: Windows CLI запускается с `shell: true`

`src/providers/cli-provider.mjs:38-42` включает оболочку. Сейчас аргументы в основном контролируются приложением, но значение модели поступает из окружения.

Рекомендация: запускать `codex.cmd`/разрешённый executable без shell-интерпретации и валидировать имя модели по безопасному формату.

#### SEC-03 — P2: товарные URL не ограничены доменом магазина

Парсер принимает URL из HTML страницы поиска без проверки origin. Скомпрометированная или изменённая страница способна вернуть внешнюю ссылку.

Рекомендация: разрешать только `https:` и согласованные hostnames, приводить URL к каноническому виду.

#### SEC-04 — P2: CORS не является защитой от небраузерного злоупотребления

Запрос без `Origin` разрешается, что корректно для HTTP, но делает endpoint публичным для скриптов и ботов.

Рекомендация: rate limit, глобальный budget cap, мониторинг аномалий, WAF/reverse-proxy ограничения. Не добавлять секрет в публичный frontend как псевдоаутентификацию.

#### SEC-05 — P3: production security headers ещё не определены полностью

Локально отсутствуют CSP и HSTS. Для встраиваемого скрипта CSP должна согласовываться с политикой основного сайта.

Рекомендация: настроить HSTS на HTTPS-прокси и документировать CSP-директивы `script-src`, `style-src`, `img-src` и `connect-src`.

## 5. Проверка API-контракта

### Фактические результаты

| Сценарий | Ожидание ТЗ 1.0 | Факт | Статус |
|---|---:|---:|---|
| `GET /health` | 200 | 200 | PASS |
| Успешный `POST /api/chat` | 200 + `answer/provider/catalog` | 200 + все поля | PASS |
| Пустое сообщение | 400 | 400 | PASS |
| Запрещённый Origin | 403 | 403 | PASS |
| Разрешённый preflight | 204 | 204 | PASS |
| Неизвестный маршрут | 404 | 404 | PASS |
| Невалидный JSON | 400 | 500 | FAIL |
| Тело больше 64 КБ | 413 | 500 | FAIL |
| Неверный Content-Type | 415 | запрос принимается | FAIL |

#### API-01 — P1: ошибки клиента маскируются как 500

Парсинг JSON и превышение размера попадают в общий `catch` в `server.mjs:42-66`.

Рекомендация: типизированные ошибки запроса и ответы 400/413 до вызова каталога и AI.

#### API-02 — P2: отсутствует единая машинная ошибка

Поле `code` присутствует только для некоторых CLI-ошибок, `requestId` отсутствует, 429 не содержит `Retry-After`.

Рекомендация: `{error, code, requestId}` для всех ошибок; `Retry-After` для 429; документированный перечень кодов.

#### API-03 — P2: контракт не версионирован

Публичный endpoint `/api/chat` можно безопасно оставить в MVP, но после подключения production-клиента изменения полей станут потенциально breaking.

Рекомендация: зафиксировать schema tests и политику совместимости; при первом breaking change перейти на `/api/v1/chat` или версию заголовка.

## 6. Accessibility check

### Пройдено

- есть доступные названия кнопок открытия, закрытия и отправки;
- поле ввода связано с label;
- после открытия фокус устанавливается в поле;
- Escape закрывает панель;
- сообщения находятся в `aria-live="polite"`;
- кнопка открытия обновляет `aria-expanded`;
- изображение персонажа декоративное (`alt=""`);
- имеются видимые focus styles;
- `prefers-reduced-motion` отключает движение;
- контраст input — 17,85:1, быстрых кнопок — 6,16:1.

### Находки

#### A11Y-01 — P2: неверная модальная семантика

При открытии код устанавливает `aria-modal="true"`, но focus trap отсутствует и фоновая страница остаётся доступной. Это противоречивый контракт для assistive technology.

Рекомендация: на desktop оставить немодальный dialog с `aria-modal="false"`; для полноэкранного mobile-режима реализовать настоящий modal с focus trap и inert background.

#### A11Y-02 — P2: фокус теряется после закрытия

После Escape активным становится `BODY`, а не кнопка открытия.

Рекомендация: сохранять предыдущий focus и возвращать его при закрытии.

#### A11Y-03 — P3: нет `aria-controls` и явного busy-status

Кнопка открытия не связана с ID панели; ожидание показывается текстом, но контейнер не получает `aria-busy`.

Рекомендация: добавить стабильный ID, `aria-controls` и `aria-busy`/`role="status"`.

#### A11Y-04 — P2: недостаточный контраст вторичного текста заголовка

Цвет `#dbeafe` на градиенте даёт примерно 4,24:1 на синем и 3,02:1 на бирюзовом участке при размере 12 px. Требуется минимум 4,5:1.

Рекомендация: сделать текст белым/почти белым и затемнить фон либо исключить бирюзовый участок под текстом; проверить весь градиент инструментально.

## 7. Performance budget

### Текущий baseline

| Ресурс | Размер | Бюджет | Статус |
|---|---:|---:|---|
| `widget.js` | 8 442 байта | 30 КБ | PASS |
| `widget.css` | 5 860 байт | 20 КБ | PASS |
| `mascot.png` | 187 728 байт | 200 КБ | PASS, запас небольшой |
| Сумма ресурсов виджета | 202 030 байт | 250 КБ | PASS |

Локальный p95 после запуска: JS 22,08 мс, CSS 12,79 мс, mascot 22,62 мс, health 2,40 мс. Эти значения подтверждают только локальную раздачу и не заменяют staging-измерения.

### Находки

#### PERF-01 — P3: короткий cache и отсутствие compression

Статика получает `max-age=300`, `Content-Encoding` отсутствует.

Рекомендация: fingerprinted assets, `Cache-Control: public, max-age=31536000, immutable`; Brotli/gzip для JS/CSS на reverse proxy.

#### PERF-02 — P2: production Web Vitals не измерены

Локальный сервер не показывает влияние виджета на реальный LCP, CLS и main thread магазина.

Рекомендация: Lighthouse/WebPageTest на staging с виджетом и без него; релиз блокируется при ухудшении LCP более 100 мс, CLS > 0 от виджета или long task > 50 мс.

#### PERF-03 — P3: в public находится исходное изображение 1,2 МБ

`mascot-chroma.png` исключён из git и не загружается демо-страницей, но физически доступен локальному статическому серверу.

Рекомендация: не включать исходник в production artifact; добавить allowlist публикуемых файлов или отдельную build-директорию.

## 8. Приоритет исправлений

### P1 — до любого публичного запуска

1. Структурно разделить AI-инструкции и недоверенные данные.
2. Добавить concurrency limit/backpressure.
3. Заменить in-memory limiter на production-схему с TTL/proxy-awareness.
4. Исправить 400/413/415 и единый error contract.

### P2 — до production-приёмки

1. Убрать `shell: true` из CLI-провайдера.
2. Проверять origin товарных URL.
3. Выделить OpenCart adapter и fixture tests.
4. Исправить модальность, возврат фокуса и контраст.
5. Ввести requestId, error codes и Retry-After.
6. Выполнить staging Web Vitals и browser matrix.

### P3 — улучшения эксплуатационного качества

1. Добавить liveness/readiness разделение и graceful shutdown.
2. Добавить `aria-controls` и `aria-busy`.
3. Настроить immutable cache и compression.
4. Исключить исходное chroma-изображение из production artifact.
